# LogiTrack — ТЗ на доработку демо

> **Статус (12.11.2026):** задачи 1–9 сделаны в демо. Блоки «Позже (не делать)» — не трогались.

Демо-CRM для американского грузоперевозчика (3–20 тягачей). Интерфейс на украинском. Бэкенда нет: все данные — демо-данные в коде, состояние хранится в Redux + localStorage.

Задачи ниже согласованы. Делать по порядку, каждую задачу — до проверенного результата.

## Общие правила (для всех задач)

1. **Тексты.** Все тексты интерфейса — только в `src/i18n/uk.ts`, в компонентах брать через `t` из `src/i18n`. Никакого английского в интерфейсе. Имена людей, компаний, складов, американских городов, номера MC/USDOT — не переводить.
2. **Единицы.** Мили и доллары. Форматирование — через `formatMiles`, `formatMoney`, `formatHours`, `formatWhen` из `src/runs/demo.ts`.
3. **Статусы в коде** остаются английскими ключами (`'In transit'` и т.п.), на экран выводятся через мапы в `uk.ts` (`t.status.*`). Новые статусы делать так же.
4. **Демо-данные.** Новые сущности (грузы в очереди, водители, выплаты, расходы, чаты) — отдельными сид-файлами рядом с `src/runs/demo.ts`. Данных должно хватать, чтобы каждый экран и каждое сообщение на «Огляді» были заполнены.
5. **Сброс демо.** «Скинути демо» / «Скинути демо-дані» возвращает в исходное состояние все новые разделы. При изменении формы сохранённого состояния поднять `STORAGE_KEY` в `src/store/store.ts`.
6. **Роли.** Есть `manager` (владелец/менеджер), `dispatcher`, `driver` (`src/store/slices/authSlice.ts`). Права на новые разделы добавлять в `RolePermissions`.
7. **Стили.** Порядок CSS-свойств — по `.cursor/rules/css-property-order.mdc`. Цвета — из переменных `src/styles/labels.scss`.
8. **Проверка перед сдачей задачи:** `npx tsc -b`, `npx vitest run`, `npx vite build` без ошибок; тесты обновить и дописать под новое поведение; каждый затронутый экран открыть и осмотреть глазами.

## Задача 1. Иерархия кнопок

**Проблема.** Активный фильтр «Усі» и кнопка «Імпорт ставки» выглядят одинаково (чёрные) — не видно, что главное действие.

**Сделать.** Три уровня кнопок, единые для всего проекта:
- **Primary** — главное действие экрана, акцентный цвет `--color-primary`. Примеры: «Імпорт ставки», «Виставити рахунок», «Призначити вантаж», «Додати вантаж», «Підтвердити доставку».
- **Secondary** — второстепенное действие, обводка/светлый фон. Примеры: «Відкрити рейс», «Заповнити форму», «Знайти зворотний вантаж», «Усі рейси».
- **Tertiary** — малозначимое действие, текст без фона. Примеры: «Скинути демо», «Скасувати», «Видалити».
- **Фильтры статусов** («Усі», «У дорозі», …) — переключатель (segmented control), а не кнопки действий. Активный фильтр — свой стиль, отличный от primary.
- На одном экране — не больше одной-двух primary-кнопок.

**Готово, когда:** на каждом экране главное действие визуально выделено, фильтры не путаются с кнопками; стили кнопок заданы модификаторами (`runs__button--primary/--secondary/--tertiary`) и применены везде.

## Задача 3. Новый раздел «Вхідні вантажі» (очередь грузов)

**Проблема.** «+ Новий рейс» создаёт пустой рейс без груза. Диспетчер берёт данные из почты/мессенджера и вводит руками.

**Идея.** Все грузы, откуда бы они ни пришли, попадают в одну очередь. Диспетчер проверяет груз и из него собирает рейс. Ставку с брокером обычно согласуют заранее (телефон/почта), потом брокер присылает подтверждение ставки (rate con, PDF) — поэтому главное действие «Перевірити і призначити». Подтверждение ставки — договор, парсер может ошибиться: ручной ввод убираем, проверку человеком оставляем.

**Меню.** Пункт «Вхідні вантажі» между «Огляд» и «Рейси», со счётчиком новых грузов.

**Источники (очередь одна):**
1. Письмо с PDF на адрес перевозчика (вида `loads@…`). В демо — имитация: 2–3 «входящих письма» в сиде + кнопка «Імітувати новий лист» (добавляет груз из файла-образца в `public/samples/`).
2. Загрузка PDF вручную — сюда переезжает существующий «Імпорт ставки» (`RateConImport`, `RateConReview`).
3. Быстрое добавление вручную (груз согласовали по телефону) — сюда переезжает «Новий вантаж» (`AddLoadForm`).

**Статусы груза:** «Новий» (нужна проверка, подсвечен) → «Готовий» (проверен) → «Призначено» (в рейсе, скрыт из основного списка) / «Відхилено».

**Карточка груза:**
- Источник (лист / PDF / вручну), брокер, маршрут, даты, ставка, ссылка на PDF.
- Поля, которые парсер не нашёл, подсвечены (как сейчас в окне импорта).
- Кнопки: «Призначити на тягач» (primary), «Відхилити» (tertiary).
- «Призначити на тягач»: новый рейс (свободный тягач + водитель) или добавить в активный рейс. Показывать прогноз «$/милю загалом» и конфликт годин водіння (логика уже есть в `RateConReview`). Водителей со статусом «Документи прострочені» (задача 4) назначать нельзя.

**Рейсы:** рейс создаётся только из груза. С экрана «Рейси» убрать «+ Новий рейс», «Імпорт ставки», «Новий вантаж».

**Огляд:** сообщение «N вантажів чекають на призначення» со ссылкой в очередь.

**Готово, когда:** груз можно получить всеми тремя способами, проверить, назначить на новый или активный рейс и отклонить; счётчик в меню и сообщение на «Огляді» обновляются.

**Позже (не делать):** биржи грузов (DAT, Truckstop), EDI-заявки от крупных клиентов с кнопками «Прийняти / Відхилити».

## Задача 4. Новый раздел «Водії»

**Проблема.** Водитель сейчас — только имя в рейсе. Не видно, кто свободен, где он, сколько ему должны, кто простаивает.

**Меню.** Пункт «Водії» после «Рейси». Водитель (роль `driver`) раздел не видит.

**Список:** имя, тягач, статус, текущий рейс и где сейчас, остаток годин водіння, сроки документов, «До виплати».

**Статус — вычисляется, не ставится руками:**
- «Вільний» — нет активного рейса, есть часы, документы в порядке.
- «У рейсі» — в активном рейсе.
- «Відпочинок» — часы закончились, ждёт 10-годинного отдыха.
- «Документи прострочені» — просрочены права (CDL) или медсправка. Назначать на рейс нельзя.

**Где водитель:** берётся из рейса/тягача (последняя точка рейса или запись журнала), в карточке водителя не хранится. Позже — из ELD (электронный бортовой журнал: GPS и часы водіння).

**Карточка водителя:** профиль (имя, телефон, тягач); документы (номер и срок CDL, срок медсправки, подсветка за 30 дней до окончания); история рейсов; выплаты.

**Выплаты:**
- MVP: оплата за милю (ставка из «Акаунт» → «Оплата водію за милю»).
- Список «Виплати водіям»: водитель, период (неделя), мили, сумма, статус «Нараховано / Виплачено», кнопка «Позначити виплаченим».

**Огляд — новые сообщения:**
- «Тягач 226 / Priya Nair без рейсу 3 дні» (порог дней — настройка в «Акаунт»).
- «У Dana Brooks медсправка закінчується через 12 днів».
- «До виплати водіям цього тижня: $X».

**Демо-данные:** все водители из `fleetRoster`; у одного истекает медсправка, у одного просрочена, один простаивает.

**Готово, когда:** статусы считаются из данных, просроченного водителя нельзя назначить, выплату можно отметить, три типа сообщений видны на «Огляді».

**Позже (не делать):** другие схемы оплаты (процент, фикс), удержания, PDF-расчёт, аналитика по водителю.

## Задача 5. Новый раздел «Фінанси»

**Проблема.** Владелец не видит, зарабатывает он в этом месяце или работает в минус.

**Доступ.** Только `manager`. Диспетчер и водитель раздел не видят. Публично — никогда.

**Главный ориентир — точка безубыточности:**
- Кружок прогресса за месяц с двумя отметками: «Беззбитковість» и «Ціль».
- Под кружком: «До беззбитковості: ще $X ≈ N миль»; после прохождения — «Прибуток за місяць: $X».
- Безубыточность = постоянные расходы за месяц + переменные расходы на пройденные мили.

**Цифры:** Виручка за місяць, Витрати за місяць, Чистий прибуток, Собівартість милі (все расходы ÷ все мили).

**График:** столбики «Виручка / Витрати» по неделям текущего месяца. Перед графиком прочитать и соблюдать правила визуализации проекта (без декоративных спарклайнов — см. историю коммитов).

**Настройка «Обов'язкові витрати»** (в разделе или в «Акаунт»):
- постоянные в месяц: лизинг/платёж за тягач, страховка, разрешения, подписка ELD, стоянка, інше;
- переменные на милю: пальне, оплата водію, платні дороги, ремонт (пальне и оплата водію уже есть в «Акаунт» — не дублировать);
- ціль на місяць.

**Честность цифр:** пока расходы считаются по ставке за милю, а не из реальных чеков, рядом с цифрами пометка «оцінка».

**Огляд:** для `manager` — блок «До беззбитковості: ще $X» со ссылкой в «Фінанси».

**Демо-данные:** месяц с ~3 неделями истории, чтобы график и кружок были заполнены и точка безубыточности была близко.

**Готово, когда:** изменение обязательных расходов сразу меняет кружок, цифры и фразу; диспетчер раздел не видит.

**Позже (не делать):** прибыльность по тягачу/водителю/клиенту/маршруту, сравнение месяцев.

## Задача 6. Чати з водіями (демо-имитация)

**Идея (как в KeyCRM с Viber).** Водитель пишет в привычный мессенджер, диспетчер отвечает из CRM. Под США — и WhatsApp, и SMS.

**В демо (без реальной интеграции):**
- Пункт меню «Чати»: список переписок с водителями, у каждого сообщения значок канала (WhatsApp / SMS), счётчик непрочитанных.
- Окно переписки: история + поле ответа. Ответ диспетчера добавляется в историю.
- Внутри рейса блок «Дзвінки водіїв і журнал диспетчера» превращается в ленту рейса: записи диспетчера + сообщения водителя этого рейса за время рейса (подтягиваются автоматически). Сообщения водителя и диспетчера визуально различаются, как в чате.
- Демо-данные: переписка с 3–4 водителями, в т.ч. по Тягач 214 (разгрузился, ждёт обратный груз) и сообщение про ожидание на складе (основание для доплаты за простій).

**Готово, когда:** диспетчер видит все чаты, отвечает, а сообщения водителя активного рейса видны в ленте рейса.

**Позже (не делать, только для понимания):** WhatsApp Business API (Meta: верификация бизнеса, платные сообщения, первое сообщение — только одобренным шаблоном) и SMS через сервис вроде Twilio. Условия проверить перед разработкой. Мобильная страница водителя по ссылке (статусы, фото документов).

## Задача 7. Связь с брокером по грузу + уведомления (toasts)

**Проблема.** По дороге постоянно возникают вопросы к тому, кто дал груз (брокер или грузоотправитель напрямую): задержка, поломка, простой, вес не совпал. Сейчас это идёт мимо CRM — по почте и телефону, и доказательств для доплат (простой) нет.

**Сделать (демо, без реальной интеграции):**
- В карточке груза в рейсе — кнопка «Брокер»: открывает переписку по этому грузу. Брокер в CRM не заходит: письма уходят на его email из подтверждения ставки, ответы возвращаются в переписку груза.
- Готовые шаблоны событий: «Затримка», «Почався простій», «Поломка», «Кількість вантажу не збігається», «Доставлено». Шаблон подставляет текст, диспетчер правит и отправляет.
- «Записати дзвінок» — короткая запись о чём договорились по телефону, в ту же переписку.
- Ответ брокера в демо приходит имитацией через несколько секунд.
- Уведомления (toasts) в правом нижнем углу: успех — зелёный, предупреждение — жёлтый, ошибка — красный, информация — нейтральный. Пропадают сами через несколько секунд, можно закрыть.
- Где показываются: письмо отправлено, звонок записан, пришёл ответ брокера, груз назначен из очереди, груз отклонён, счёт выставлен, выплата отмечена; ошибка — нет email брокера.

**Позже (не делать):** реальная отправка и приём почты (почтовый ящик перевозчика), трекинг-приложения брокеров (MacroPoint, Trucker Tools) — условия проверить перед разработкой.

## Задача 8. Кнопка «Підтримка» (сообщить о проблеме)

**Проблема.** Если в CRM что-то сломалось (например, не отправляется письмо брокеру), диспетчеру некуда сообщить, а работа стоит.

**Сделать (демо):**
- В меню внизу, над «Вийти», — пункт «Підтримка». Доступен всем ролям.
- Окно «Повідомити про проблему»: тип (не працює / питання / пропозиція), отметка «Терміново — заважає працювати», описание.
- К обращению автоматически прикладываются: раздел, где был пользователь, пользователь и роль, время, браузер. Показать это списком в окне, чтобы человек видел, что отправляется.
- После отправки — уведомление с номером обращения.

**Открытый вопрос (решить до рабочей версии):** куда реально уходят обращения — email, Telegram-бот команды или трекер задач (Jira/ClickUp). Для срочных — дублировать в мессенджер дежурного.

## Идеи на обсуждение (не делать без решения)

### Отчётность
- Идея Юры: кнопка «Звітність» — сформировать файл по рейсам и отправить.
- Разбор: для перевозчика в США главный обязательный отчёт — IFTA (квартальный отчёт по топливному налогу: мили и топливо по каждому штату). Требование проверить по официальным источникам перед разработкой. Для него нужны мили по штатам — реально только с GPS/ELD.
- Остальное — внутренние отчёты: прибыль по тягачам/клиентам/маршрутам, расчётные листы водителям, пакет документов для факторинга (счёт + подтверждение ставки + POD).
- Предложение: раздел «Звіти» с выгрузкой в CSV/PDF, первым — пакет для факторинга и расчётные листы водителям (данные уже есть), IFTA — после интеграции с ELD.
